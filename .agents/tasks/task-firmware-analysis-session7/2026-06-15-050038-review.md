# Automated firmware analysis script and overflow ruling

Session 7 adds a standalone ARM Thumb-2 disassembly tool (`debug_toolkit/fw_analyzer.py`) that programmatically verifies the 27-byte OR-merge patch and documents that the SET_REPORT handler chain contains no exploitable buffer overflow. Documentation is updated to reflect this finding: the HID overflow exploitation path moves to "blocked" and only hardware (SWD) and social (contact Ajazz) paths remain.

Watch for: the analysis script hardcodes every address and expected byte pattern, so any firmware revision silently invalidates all results without warning (**confirmed**); the `or_merge_logic` section in the script contains inaccurate register references in its human-readable summary strings (**confirmed**).

## High-level view

The new `fw_analyzer.py` is a documentation-as-code artifact: it encodes the analyst's conclusions about the firmware in a runnable form, producing a JSON report that asserts "no overflow" and "patch correct." The script is structured to confirm known-good answers rather than discover new ones — all memcpy call sites, handler addresses, and expected byte patterns are hardcoded constants. This is appropriate for its stated purpose (reproducible verification) but means it cannot detect regressions in a different firmware revision.

The overflow analysis methodology is sound for ruling out classic stack-based overflows in the SET_REPORT path. The script documents the constraints (hardcoded memcpy lengths, bounded computed-length copy, individual LDRB parsing) but does not dynamically verify them — the memcpy call list is a static table, not discovered via disassembly. A scan for all BL instructions targeting the memcpy address would close that gap.

1. **Hardcoded addresses with no firmware version check** — `fw_analyzer.py` validates the binary is exactly 108608 bytes but does not check any version identifier or MCUboot header field. Running it against a different firmware revision would produce misleading "all checks passed" or confusing failures. Add a magic/version assertion early in `run_analysis`.
2. **Inaccurate `logic_summary` register references** — The `logic_summary` strings say `LDRB R2, [R0, #0]` for the physical button load, but the actual patch bytes (`2278` = `LDRB R2, [R4]`) use R4 as the report pointer. The raw-byte comparison still passes, but the human-readable documentation misleads anyone reading the JSON report. Fix the summary strings to match the actual encoding.
3. **File handle leak in `run_analysis`** — `open(original_path, 'rb').read()` without a context manager. Trivial for a CLI script but easy to fix.

## Static verification vs. dynamic analysis

The script's `MEMCPY_CALLS_IN_HANDLER` and `MEMCPY_CALLS_IN_PROCESSOR` are hardcoded dictionaries. The disassembly functions produce context listings around those known addresses, but there is no code path that scans the binary for BL instructions targeting `0x14D58` (the memcpy address). If a future firmware version added a new memcpy call site in the handler, this tool would not detect it.

```python
MEMCPY_CALLS_IN_HANDLER = [
    {"address": 0x19494, ...},
    {"address": 0x196FE, ...},
    {"address": 0x19D86, ...},
]
```

The `find_bl_target` function already correctly decodes Thumb BL encoding, so adding a scan for all BLs to `0x14D58` within the handler address range would be straightforward and would turn the tool from "confirm manual findings" into "detect regressions."

## `or_merge_logic` documentation discrepancy

The `logic_summary` field describes the second instruction as `LDRB R2, [R0, #0]`, but the actual patched cave bytes `417922781143217081796278114361707047` decode differently:

- `4179` = LDRB R1, [R0, #5] (correct in summary)
- `2278` = LDRB R2, [R4, #0] (summary incorrectly says `[R0, #0]`)

R4 holds the physical report pointer, not R0. The verification passes because it compares raw bytes against `PATCH_APPLIED_CAVE` rather than relying on the summary strings, but anyone reading the JSON output's `logic_summary` will get a wrong mental model of which register points where. The same error repeats for the second pair (`6278` = LDRB R2, [R4, #1]`, not `[R0, #1]`).
